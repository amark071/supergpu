# CUDA 稀疏超节点 LDLT 优化总结

## 1. 项目目标

本项目面向对称稀疏不定矩阵，采用 CHOLMOD 已生成的消去树和基本超节点结构，在 GPU 上完成 FP32 超节点 LDLT 数值分解与求解。数值分解使用 Bunch–Kaufman（BK）主元判定和延迟主元策略，在保证稳定性的前提下，针对大量小超节点和少量大型超节点分别优化。

当前实现始终保持以下约束：

- 输入矩阵、分解因子、右端项和输出解均为 `float`；
- 主元判定、Schur 补更新和求解累加均采用 FP32；
- cuBLAS 使用严格 FP32 数学模式，不用 TF32 替代 FP32；
- 符号分析继续使用 CHOLMOD 的现有结果，优化集中在数值分解和数值求解阶段。

## 2. 超节点分类与计算路径

按照超节点候选列数，将节点划分为三类：

| 类型 | 列数 | 处理方式 |
|---|---:|---|
| 单列节点 | 1 | 专用小节点路径，降低通用面板算法的额外开销 |
| 中小节点 | 2～64 | 批量组织和并行处理，减少小任务启动开销 |
| 大型节点 | 大于 64 | 面板式 BK 分解，并通过多个 CUDA stream 并发处理同层独立前沿 |

该分类只决定 GPU 执行方式，不改变超节点树的依赖关系。子节点产生的贡献块仍按照消去树汇入父节点，延迟列也只能沿树向父节点传递。

## 3. 数值稳定性修复

### 3.1 原问题

早期单列节点的主元尺度只使用对角元自身。只要对角元非零，即使它相对于前沿下方的耦合项非常小，也可能被错误接受为 1×1 主元。这会产生很大的 `L` 乘子并破坏数值稳定性。

典型异常结果为：

- `||x||∞ ≈ 1616`，而验证解应为全 1；
- 绝对残差约为 `38.7`；
- 相对残差约为 `154.5`。

### 3.2 修复方法

BK 的列最大值现在覆盖整个未消去前沿：

- fully-summed 行可参与主元选择；
- 尚未 fully-summed 的更新行不能被选为主元；
- 但这些更新行必须参与主元稳定性尺度计算；
- 当前节点找不到稳定主元时，将该列延迟到父节点处理。

同一稳定性规则应用于单列、中型和大型三条数值分解路径，避免不同节点分类产生不一致的主元接受标准。

修复后，1215 阶测试矩阵得到：

- `||x||∞ = 1.00006533`；
- 绝对残差 `3.55765224e-7`；
- 缩放后向误差 `2.20836796e-7`；
- FP32 验证通过。

## 4. 数值分解优化

### 4.1 有序唯一 CSC 快速路径

输入 CSC 的每列行号已经严格递增且没有重复项时，直接走有序唯一 CSC 快速路径，避免构建通用哈希累加结构。只有存在重复坐标或不满足快速路径条件时，才进入兼容性聚合流程。

这项优化减少了输入预处理中的哈希、临时对象和 CPU 内存访问开销。

### 4.2 CUDA 异步内存池

在设备支持 CUDA memory pool 时启用 `cudaMallocAsync/cudaFreeAsync`，并提高默认内存池的释放阈值，使分解期间频繁出现的临时前沿、贡献块和描述表分配能够复用显存，而不是反复触发同步式设备分配。

### 4.3 GPU 全局编号到前沿局部编号映射

前沿装配需要频繁把全局行列编号映射到局部位置。优化后使用 GPU 常驻的 `global_to_local` 映射，减少 CPU 端查找和逐项控制，也避免为每个前沿重复建立高开销映射容器。

### 4.4 前沿编号批量回传

多个前沿的重排编号先在 GPU 上打包，再进行一次批量 D2H 传输，代替逐前沿的小规模同步拷贝。该方式减少 PCIe 小拷贝次数和主机同步点。

### 4.5 因子保存与贡献块提取异步化

已完成前沿中的因子列通过 D2D 异步拷贝保存；未消去部分在 GPU 上直接提取为父节点所需的贡献块。保存因子和提取贡献的操作尽量保持在设备端，避免不必要的数据下载和重新上传。

### 4.6 批量前沿显存区

同一批次的前沿数值、编号和主元类型不再分别进行大量小分配，而是放入批量连续显存区，并通过偏移定位各前沿数据。

主要收益包括：

- 减少设备内存分配次数；
- 改善数据局部性；
- 降低小对象生命周期管理开销；
- 便于同一批次内核统一调度。

### 4.7 固页上传缓冲区复用

前沿编号上传使用可复用的 pinned host memory，降低 pageable memory 隐式暂存以及重复注册主机内存的开销。

### 4.8 大型前沿多 stream 并发

同一消去树层内互不依赖的大型前沿分配到多个非阻塞 CUDA stream，并为每个 stream 配置独立 cuBLAS handle。当前实测配置使用 4 个大型前沿 stream。

该优化使大型节点的面板分解和矩阵更新能够相互重叠。消去树只有十余层但每层可能包含大量独立节点，因此层内并行比逐节点串行更适合当前结构。

### 4.9 CPU 去重时间戳

主机端构造前沿编号集合时，使用整数时间戳数组代替反复清空集合或哈希结构。每轮通过增加 generation 标识已访问元素，降低前沿结构去重的 CPU 调度开销。

### 4.10 分阶段计时

数值分解增加了以下阶段计时：

- 输入预处理和上传；
- 前沿装配入队；
- 子贡献释放与同步屏障；
- 单列/中小节点分解；
- 大型面板分解；
- 因子保存和贡献提取；
- 已归因阶段总时间；
- 未归因调度时间；
- GPU 数值分解总时间。

这些计时用于定位瓶颈，不参与数值计算。

## 5. 数值求解优化

### 5.1 原始调度方式

原求解器对每个有效超节点分别启动：

1. 一个前代 kernel；
2. 一个块对角 `D` 求解 kernel；
3. 一个回代 kernel。

对于约 21970 个超节点，kernel 启动数量接近 6.6 万次。大量单列节点的实际计算很少，因此求解时间主要消耗在 kernel 启动和同步，而不是浮点运算。

### 5.2 GPU 常驻求解描述表

数值分解完成后，为所有有效超节点构造紧凑的设备描述表，其中保存：

- 因子数值地址；
- 超节点全局编号地址；
- 1×1/2×2 主元类型地址；
- 前沿阶数；
- 已接受主元列数。

描述表只上传一次，之后求解直接在 GPU 上访问，不再由 CPU 逐节点读取并发起调用。

### 5.3 RHS 显存工作区复用

右端项设备缓冲区随因子对象一起保留并重复使用，避免每次 `solve()` 都调用 `cudaMalloc/cudaFree`。单次求解只需要上传 RHS、执行求解并下载结果。

### 5.4 按消去树层执行前代和回代

求解使用数值分解时记录的消去树波次：

- 前代按照叶节点到根节点的层序执行；
- 同一层的独立超节点由不同 CUDA block 并行处理；
- 对共同祖先 RHS 项的更新使用 FP32 `atomicAdd`，保证并发写入正确；
- `D` 中的 1×1 和 2×2 对角块统一批量求解；
- 回代按照根节点到叶节点的逆层序执行。

当消去树有 13 层时，调度规模从约 6.6 万次 kernel 启动降低为大约：

```text
13 次前代 + 1 次 D 求解 + 13 次回代 = 27 次 kernel 启动
```

这既保留了树依赖，又利用了同层节点并行性。

### 5.5 FP32 原子累加的影响

同层并发使浮点加法顺序可能在不同运行中发生细微变化，因此最终残差可能出现末尾数位波动。这是 FP32 非结合性导致的正常现象。当前实测残差变化远小于验证阈值，未造成稳定性退化。

## 6. 性能结果

测试矩阵规模：

- 阶数：63666；
- 输入非零元：10666320；
- 符号因子 `L` 非零元：17960154；
- 基本超节点：21970；
- 单列节点：21173；
- 2～64 列节点：82；
- 大于 64 列节点：715；
- 超节点树波次：13。

## 7. 当前精度结果

最新 63666 阶矩阵的全 1 真解验证结果：

| 指标 | 结果 |
|---|---:|
| 解的无穷范数 | `1.00067806` |
| 绝对残差 `||Ax-b||∞` | `2.20934453e-7` |
| 相对残差 `||Ax-b||∞/||b||∞` | `1.41101154e-5` |
| 缩放后向误差 | `2.39330257e-6` |
| 相对解误差 | `6.78062439e-4` |
| FP32 验证阈值 | `3.45266977e-4` |
| 残差验证 | `PASS` |

`PASS` 主要依据残差和缩放后向误差判定。对于病态或接近奇异的矩阵，相对解误差可能明显大于后向误差；这并不等价于分解残差失败。

## 8. 合成回归覆盖

不读取大型数据文件的合成 GPU 回归覆盖了：

- 中型前沿的 BK 2×2 主元；
- 重复 CSC 坐标的兼容路径；
- 子节点向父节点延迟主元；
- 非零但不稳定的单列主元延迟；
- 三级超节点贡献传播；
- 大型面板 BK 分解；
- 大型面板内部延迟列；
- 多个独立大型根节点并发。

上述测试均通过，合成测试最大绝对残差约为 `1.19209e-7`。

## 9. 当前瓶颈与后续方向

目前 GPU 数值分解已经由约 8.3 秒下降到约 2.0 秒，单 RHS 求解由约 117.8 毫秒下降到约 16.4 毫秒。完整程序仍包含文件读取、METIS/AMD 排序、CHOLMOD 符号分析、可视化数据输出和残差验证，因此程序总时间不能直接视为 GPU 数值分解时间。

若继续优化，优先方向包括：

1. 对大型超节点的前代和回代使用更加块化的访存和矩阵向量实现；
2. 减少同层前代中的原子写竞争；
3. 将大量单列因子的间接索引进一步压缩或重排，提高 RHS 和因子访问局部性；
4. 多右端项场景改用 TRSM/GEMM，使计算密度显著高于单 RHS；
5. 将排序、符号分析和数值分解结果缓存，用于同一稀疏结构下的重复数值计算。

在当前单 RHS 工作负载中，求解时间已经只占完整程序时间的很小部分。若目标是继续降低端到端时间，后续工作应优先分析排序、符号分析、输入处理以及 GPU 数值分解中的大型面板更新。
